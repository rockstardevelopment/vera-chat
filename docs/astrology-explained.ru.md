# Астрологическая консультация — объяснение простыми словами

Дополнение к [`astrology.md`](./astrology.md), написанное для разработчика, который не знает ни
астрологии, ни этой части кодовой базы. Здесь определяются все термины, которые использует дизайн.

## 1. Резюме в одном предложении

Приложение делает **математику по натальным картам** с помощью специализированной библиотеки, затем
передаёт LLM **точные вычисленные числа** как скрытый контекст, и единственная задача LLM —
**объяснить эти числа в разговоре**. LLM никогда ничего не вычисляет астрологически.

## 2. Астрологическая половина — что это за числа

**Натальная карта.**
Снимок того, где находились Солнце, Луна и планеты в небе в точный момент и в точном месте вашего
рождения. «Где» измеряется как угол вдоль окружности, называемой **эклиптикой** (путь, который
Солнце визуально проходит за год), разделённой на 12 знаков по 30°: 0° Овна, 30° Тельца и так далее
до 360°. Карта — это по сути список вида: Солнце в 21° Тельца, Луна в 8° Рыб, Марс в 3° Льва…

**Эфемериды (ephemeris).**
Астрономический ежегодник, который отвечает на вопрос «где была каждая планета 1990-05-12 в
14:30 UTC?». `caelus` — это TypeScript-библиотека, содержащая такие эфемериды (в виде математических
формул) плюс астрологические расчёты поверх них. **Swiss Ephemeris** — отраслевой стандарт, более
старая версия того же самого, написанная на C; наш план использует `caelus`, потому что он под
лицензией MIT (можно свободно использовать в закрытом продукте), тогда как Swiss Ephemeris под AGPL
(нужно либо открывать исходники, либо покупать коммерческую лицензию). Именно эта разница в лицензиях
— единственная причина выбора движка.

**Тропический и сидерический зодиак.**
Две конвенции о том, где начинаются 12 знаков. «Тропический» привязывает 0° Овна к весеннему
равноденствию — это то, что использует западная астрология. «Сидерический» привязан к неподвижным
звёздам (ведическая астрология). Мы выбрали **тропический**, потому что в job stories используются
западные концепции (транзиты, соляр, самореализация).

**Дома, Асцендент (ASC), MC.**
Если знаки описывают, _какого рода энергию_ несёт планета, то **дома** — это 12 секторов, описывающих,
_в какой сфере жизни_ она оказалась (деньги, дом, отношения, карьера…). Дома зависят от **точного
времени рождения**, потому что основаны на том, какая часть неба восходила. **Асцендент** — точка,
восходящая на восточном горизонте в момент рождения; **MC (Середина неба)** — высшая точка. Обе
меняются примерно каждые 2 минуты, поэтому ошибка в час во времени рождения может сдвинуть их на
целый знак.

**Система домов.**
Есть несколько формул для построения 12 границ домов. **Плацидус** — самый распространённый в западной
астрологии, и мы берём его по умолчанию. **Whole sign («знак целиком»)** — простая система, где каждый
знак равен одному дому; она не зависит от времени рождения, поэтому используется как запасной вариант,
когда пользователь не знает своё время. **Высокие широты** (Мурманск, Тромсё) математически ломают
Плацидус — отсюда тоже откат к whole sign.

**Аспекты и орбисы.**
**Аспект** — значимый угол между двумя планетами: 0° соединение, 60° секстиль, 90° квадратура, 120°
трин, 180° оппозиция. «Солнце в квадратуре к Сатурну» означает, что они примерно в 90° друг от друга,
и у этой комбинации есть трактовка. **Орбис** — допуск: мы всё ещё считаем это квадратурой, если угол
90° ± 6°, например. Орбисы — это дизайнерское решение, поэтому в документе сказано, что они
версионируются.

**Транзиты.**
Где планеты находятся _прямо сейчас_ по сравнению с их положением при рождении. «Сатурн сейчас в
квадратуре к вашему натальному Солнцу» — это **транзит**. Это стандартная техника прогнозирования и
основа JS-11 («текущий период»), JS-12 («краткосрочный прогноз») и других. Без транзитов астролог
может описать только личность; с ними — говорить о времени.

**Случай неизвестного времени.**
Если пользователь не знает время рождения, мы не можем честно вычислить Асцендент и дома. В дизайне
сказано: использовать whole-sign дома, убрать из ответа все утверждения про Асцендент и дома и показать
видимое предупреждение. Это продуктовое решение о доверии: уверенно неверный Асцендент хуже, чем
честный пробел.

**Прочие астрологические термины из дизайна:**

- **Синастрия** — сравнение карт двух людей для совместимости (JS-09/10).
- **Соляр (solar return)** — карта момента, когда Солнце возвращается в своё натальное положение
  каждый год; используется для «вашего личного года» (JS-18).
- **Ректификация** — восстановление неизвестного времени рождения по событиям жизни; явно вне MVP.
- **Элективные окна** («выбор периода», JS-16) — сканирование диапазона дат в поиске лучших дней для
  действия (подписание договора, свадьба).
- **Ведическая/сидерическая** традиция — индийская астрология; вне MVP.

## 3. Программная половина — как всё соединяется

**Монорепозиторий / workspace.**
Один git-репозиторий, содержащий несколько npm-пакетов. В этом репозитории есть `api` (устаревшая
обвязка сервера), `packages/api` (новый backend-код), `packages/data-schemas` (база данных),
`packages/data-provider` (типы, общие для фронтенда и бэкенда), `client` (React-приложение). Дизайн
добавляет ещё один:

**`packages/astrology` — калькулятор.**
Новый пакет с чистыми функциями. «Чистые» означает: данные на входе, данные на выходе, без базы
данных, без HTTP, без конфигурации, без знания о существовании LibreChat. Вы вызываете
`computeChart(birthData, options)` и получаете `ChartFacts`. Благодаря изоляции его легко тестировать
(сравнивать с эталонными картами) и легко заменить позже на другой движок. Это и есть смысл «шва
движка» (engine seam): есть ровно одна небольшая дверь (`computeChart`, `computeTransits`, …), через
которую остальное приложение обращается к астрологической математике, поэтому замена `caelus` на Swiss
Ephemeris затронет только то, что за дверью.

**`ChartFacts` — вычисленный результат.**
JSON-объект: знак, градус, дом каждой планеты, ретроградность, все аспекты, и блок `meta`, где
записано, какими версиями движка и настроек это получено. Это единственный источник правды для всего,
что сообщается пользователю.

**Дайджест (digest).**
LLM не умеет вычислять положения планет и не должен угадывать. **Дайджест** — компактная текстовая
сводка `ChartFacts` (например, таблица положений плюс значимые аспекты) вместе с транзитами на
сегодня. Она вставляется в инструкции модели на каждом ходу. Бюджеты («короткий» и «полный» дайджест)
регулируют, сколько именно вставляется, потому что инструкции стоят токенов и денег.

**`sharedRunContext` — куда вставляется дайджест.**
В LibreChat уже есть механизм добавления текста для конкретного запуска в системные инструкции модели
(сейчас он используется для содержимого файлов и памяти пользователя). В коде он собирается в
`api/server/controllers/agents/client.js` примерно на строке 2815. Наш дизайн добавляет туда один
вызов: «спроси у `packages/api/src/astrology` текст дайджеста и допиши его». Контроллер остаётся
«тупым»; астрологическая логика остаётся в TypeScript внутри `packages/api`. Это и означает правило
репозитория «`/api` — это проводка, а не поведение».

**`packages/api/src/astrology` — адаптер фичи.**
Слой, который знает о пользователях, базе данных, конфигурации и кэше: загружает профиль пользователя,
считает или достаёт из кэша факты, строит дайджест, отдаёт HTTP-маршруты (`/api/astrology/profiles`,
`/chart`, `/transits`). «Адаптер» здесь означает, что он адаптирует чистый калькулятор к конкретному
приложению.

**`AstroProfile` — сохранённые данные рождения.**
Запись в MongoDB на каждого человека, чья карта нам известна: кому принадлежит (`user`), метка («Я»,
«Мама»), тип отношений, дата/время/место/таймзона рождения, флаг точности и флаги согласия. Одна
запись помечается как основная. **ObjectId** — тип идентификатора в MongoDB; **tenantId** — метка
мультитенантности этого форка (приложение может обслуживать несколько организаций, и запросы
автоматически ограничиваются так, чтобы тенант A никогда не видел данные тенанта B). **Шифрование при
хранении** означает, что данные рождения лежат в базе зашифрованными, чтобы дамп базы их не раскрыл.
**PII** — персональные данные; дата+время+место рождения — ровно они.

**TLS.**
Сейчас дроплеты работают по обычному HTTP, поэтому всё, что отправляется на сервер (включая данные
рождения), передаётся по сети в читаемом виде. Дизайн помечает это как жёсткое предусловие: никаких
данных рождения, пока не появится HTTPS/Cloudflare Tunnel.

**`configSchema` / `librechat.yaml`.**
Операторы настраивают LibreChat через YAML-файл, который валидируется схемой. Правила репозитория
требуют, чтобы каждый новый переключатель жил там с безопасным значением по умолчанию, поэтому дизайн
добавляет секцию `astrology:`, где `enabled: false` означает, что вся фича невидима, пока оператор её
не включит. `insightsEnabled` — существующий пример того, как такой флаг доходит до фронтенда.

**Агент и model spec.**
В LibreChat **агент** — это настроенный ассистент (инструкции, инструменты, модель). **Model spec** —
это пункт в выпадающем списке выбора модели, заданный в YAML, который может нести пресет — включая
`preset.agent_id`, привязывающий конкретного сохранённого агента. Мы используем это, чтобы «Вера,
астролог» была стабильной, нередактируемой персоной, которую выбирает пользователь, и чтобы сервер
распознавал астрологические разговоры («эффективный spec — `vera-astrologer`») и вставлял дайджест
только тогда.

**Skill (навык).**
Возможность LibreChat: markdown-документ с инструкциями, который модель может загрузить по
необходимости. Мы используем его для _методологии_ астролога — тон, как взвешивать положения, как
строить ответ, правила безопасности. Это контент, а не код, поэтому редакторы могут менять его без
деплоя.

**База знаний трактовок и атомы.**
Это движок качества. Вместо того чтобы доверять памяти модели об астрологии («Солнце во Льве
означает…»), мы держим выверенную библиотеку маленьких текстовых фрагментов — **атомов**, — ключом к
которым служит комбинация в карте (`sun.in.leo`, `moon.in.4`, `sun.trine.moon`).
`composeBrief(facts, jobId)` выбирает и ранжирует атомы, релевантные текущей задаче, и формирует
**бриф**; затем модель пишет связный текст по этому брифу. Выгоды: консистентные ответы, редакторский
контроль, лёгкая локализация на русский/английский, а утверждения можно отследить и протестировать.
Это же — самая большая статья затрат на контент, что дизайн и отмечает.

**Каталог задач (job catalog).**
29 job stories хранятся как записи-данные (`JobDefinition`: какие профиль/транзиты/период/вопрос нужны,
стартовый промпт, категория, фаза). Страница-хаб рисует карточки из этих данных; сервер обращается к
каталогу, чтобы понять, какой контекст подготовить. Добавление новой истории не должно требовать
написания кода в нескольких местах — в этом аргумент масштабируемости дизайна.

**Кэширование и хэш-ключ.**
Считать карту быстро, но делать это на каждом сообщении расточительно. Дизайн хранит результаты под
ключом — **хэшем** (отпечатком) данных рождения + настроек + версии движка. «Версия в ключе» означает:
обнови движок — и старые закэшированные результаты автоматически игнорируются, а не смешиваются
втихую с новыми.

**Golden fixtures, спайк, e2e, Lighthouse.**

- **Спайк** — короткий ограниченный по времени эксперимент, снижающий риск решения. Здесь: проверить
  `caelus` на десяти эталонных картах до начала любой разработки.
- **Golden fixtures (эталонные фикстуры)** — сохранённые пары «вход и заведомо правильный выход»,
  используемые дальше как регрессионные тесты.
- **e2e** — тест, который прогоняет реальный интерфейс (онбординг, вопрос).
- **Lighthouse** — измерение производительности; репозиторий запускает его в CI и начисляет «штраф» за
  каждый запрос к базе данных на видимой странице, поэтому дизайн требует, чтобы чтение профиля не
  добавляло последовательный (serial) запрос к первой отрисовке (LCP = Largest Contentful Paint —
  момент, когда основной контент становится видимым).

## 4. Сквозной пример: что происходит на самом деле

Анна впервые открывает приложение.

1. Клиент не находит `AstroProfile` для неё и показывает **мастер (wizard)**: дата рождения, время
   (или «не знаю»), и поле места с автодополнением.
2. Она отправляет «12.05.1990, 14:30, Москва». Сервер превращает «Москва» в координаты и
   **IANA-таймзону** (стандартная база таймзон, например `Europe/Moscow`) и конвертирует местное время
   в точный момент UTC, применяя исторические правила летнего времени, действовавшие в 1990 году —
   Россия несколько раз меняла правила, включая 2011 и 2014, и наивный фиксированный сдвиг дал бы
   неверную карту. Профиль сохраняется зашифрованным.
3. На лендинге она видит карточку карты и **каталог задач** с тематическими карточками. Она нажимает
   «Понять себя» (JS-01).
4. Открывается новый чат по **deep link**, который несёт model spec астролога и стартовый вопрос.
5. Когда она отправляет сообщение, сервер:
   - аутентифицирует её (существующий `requireJwtAuth`),
   - видит, что в разговоре используется астрологический spec, поэтому загружает её профиль по
     умолчанию (параллельно с другими чтениями базы, которые уже выполняет, и с кэшированием),
   - вычисляет `ChartFacts` калькулятором (или читает из кэша),
   - строит дайджест её натальных положений и второй дайджест **транзитов** на сегодня,
   - дописывает оба в `sharedRunContext`.
6. Модель теперь получает: инструкции агента-астролога, методологический Skill, точные факты карты,
   сегодняшние транзиты и её вопрос. Она пишет трактовку. Она не может выдумать положение, потому что
   настоящие числа у неё перед глазами — а если что-то утверждает, утверждение восходит к атому в
   брифе.
7. Клиент отрисовывает ответ, а **колесо карты** рисуется React-SVG-компонентом напрямую из JSON
   карты — не из того, что написала модель.
8. Через месяц она возвращается с новым вопросом. Тот же разговор сохраняется, память несёт её темы,
   а сервер пересчитывает только дайджест _на сегодня_; натальная половина берётся из кэша. Это
   преемственность JS-26 без нового хранилища.

## 5. Глоссарий (кратко)

| Термин                     | Значение                                                                      |
| -------------------------- | ----------------------------------------------------------------------------- |
| Натальная карта            | Снимок неба при рождении; положения планет в знаках/домах                     |
| Эклиптика                  | Окружность 360°, по которой измеряются небесные положения                     |
| Эфемериды                  | Альманах/математика, вычисляющая положения для любой даты                     |
| `caelus`                   | MIT TypeScript-библиотека эфемерид и карт, которую планируем                  |
| Swiss Ephemeris            | Отраслевой стандарт на C; AGPL или платная коммерческая лицензия              |
| Тропический / сидерический | Две конвенции зодиака; выбран тропический (западный)                          |
| Дом                        | Один из 12 секторов сфер жизни; нужен точный день рождения                    |
| ASC / MC                   | Асцендент / Середина неба; чувствительные ко времени точки                    |
| Плацидус / whole sign      | Системы домов; Плацидус по умолчанию, whole sign при неизвестном времени      |
| Аспект / орбис             | Значимый угол между планетами / его допуск                                    |
| Транзит                    | Текущее небо относительно натальной карты; основа прогнозов                   |
| Синастрия                  | Сравнение двух карт на совместимость                                          |
| Соляр                      | Годовая карта возвращения Солнца в натальное положение                        |
| `ChartFacts`               | Вычисленный JSON-результат; источник правды                                   |
| Дайджест                   | Компактный текст фактов, вставляемый в промпт модели                          |
| Атом / бриф                | Выверенный фрагмент трактовки / набор для задачи                              |
| Skill                      | Markdown-инструкции LibreChat, загружаемые моделью                            |
| Агент / model spec         | Настроенный ассистент / пункт выбора, указывающий на него                     |
| `sharedRunContext`         | Существующий канал LibreChat для доп. системного контекста на запуск          |
| Адаптер / шов              | Конкретная реализация за маленьким интерфейсом / место стыковки               |
| Чистый пакет               | Код без зависимостей от приложения/БД/HTTP; легко тестируется и заменяется    |
| `AstroProfile`             | Хранимая запись с данными рождения человека                                   |
| Тенант                     | Метка изоляции организации на каждой записи                                   |
| PII / TLS                  | Персональные данные / шифрованный транспорт; TLS — предусловие                |
| Хэш / ключ кэша            | Отпечаток для хранения и переиспользования результатов                        |
| Спайк                      | Ограниченный по времени эксперимент по рискованному вопросу (точность движка) |
| Golden fixture             | Сохранённая пара «вход / заведомо верный выход» для тестов                    |
| e2e / LCP / Lighthouse     | UI-тест / первая отрисовка контента / проверка производительности в CI        |

верификация. Это объяснение — пояснение к контракту; при расхождении побеждает дизайн. Глоссарий в §5
— быстрая справка по любому термину из обоих документов.
